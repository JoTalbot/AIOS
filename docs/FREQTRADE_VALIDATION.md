# Freqtrade-валидация порта T2 (2026-08-16)

Статус: **порт подтверждён** (число сделок и доходность совпадают с эталоном
на идентичных данных, отклонение 0.1–3.9%). Блокер TA-Lib снят.

## Зачем это было нужно

1. Независимая валидация T2 в «боевом» движке freqtrade (backtesting + dry-run).
2. A/B-сравнение с комьюнити-стратегиями (NostalgiaForInfinity и пр.) — теперь возможно.
3. Гипероптимизация окон SMA в контролируемой среде.

## Что выяснилось в процессе (важные находки)

### 1. Первый порт был НЕВЕРНЫМ (пересечения вместо уровней)
Исходный `freqtrade_t2.py` входил по **пересечению** SMA
(`close.shift(1) <= sma.shift(1) ...`), а прода T2 входит по **уровню**
(`close > SMA50` при нахождении в кэше). После выхода по гистерезису
пересечение ждёт нового кросса, а прода перезаходит сразу — расхождение
в хлыстовидных зонах.

### 2. Сигнальный столбец выхода в freqtrade блокируется входом
`should_exit()` игнорирует сигнал выхода, если на той же свече истинен и
сигнал входа (`exit_ and not enter`). В зоне между SMA50 и SMA40 (когда
SMA40 > SMA50, т.е. сразу после локальной вершины) оба условия истинны
одновременно → выход задерживался (пример BTC июль 2019: выход 24-го вместо
21-го). **Решение: выход реализован в `custom_exit()`** (проверяется на
каждой закрытой свече независимо от сигнала входа) + запрет выхода в свече
входа (прода проверяет выход только из состояния LONG со «вчера»).

### 3. Модель исполнения freqtrade = следующий открытие, НЕ закрытие дня сигнала
Это **не** искажает результат для крипты: гэпы close→open ничтожны
(медиана 0.004–0.01%, p95 0.11–0.29%). На одинаковом диапазоне close-fill
и open-fill расходятся на 0.4–4.1%.

### 4. Главный эффект расхождений — стартовое окно, а не исполнение
Эталонная прода считает сигналы с 50-го бара истории; freqtrade требует
200 свечей разогрева и не торгует первые 200 баров. Для BTC это теряет
февраль–июль 2019 (+~145%), для NEAR — ралли дек 2020–апр 2021 (+~800%),
для SOL — 2020-05→2020-11 (+~700%). **Вывод: цифры продовых бэктестов
завышены ровно на вклад первых 200 баров истории каждого актива; порт
freqtrade — консервативная (и честная) оценка.**

## Методика валидации

На идентичных данных сравнивались три кривые:
- **close-fill** — продовой алгоритм (run_daily: сделка по закрытию дня сигнала);
- **open-fill** — модель freqtrade (сигнал по close[t-1], исполнение по open[t],
  без выхода в свече входа);
- **freqtrade backtest** — движок freqtrade 2026.7.

Критерий: freqtrade ≈ open-fill (одна модель исполнения), допуск 10%.

## Ограничения / оговорки

1. Продовые цифры T2 (+1574% BTC и т.д.) включают сделки в первые 200 баров
   истории каждого актива; freqtrade-бэктест этих сделок не видит.
2. В dry-run freqtrade исполняет по рыночной цене в момент сигнала —
   в реальной торговле будет проскальзывание и комиссия 0.1% (учтены в
   бэктесте через `--fee 0.0015`).
3. Патч ccxt живёт в venv — после переустановки venv его нужно воспроизвести
   (см. комментарии в файлах ccxt).
4. Валидация не проверяет маржу/фьючерсы и другие биржи.

## Гипероптимизация окон (2026-08-16, вердикт)

Цель: проверить, находит ли hyperopt окна SMA лучше базовых (50/40; BNB/NEAR 50/50).

Инструменты: `scripts/freqtrade_t2_hyper.py` (`T2MomentumHyper`: hyperopt-параметры
`in_w`/`out_w`, кламп `out<=in`), раннер `data/freqtrade/run_hyperopt.sh`,
`scripts/freqtrade_validation/parse_hyperopt.py` (лучшие окна из лога),
`parse_zips.py` (сводка бэктестов), `validate_hyperopt.py` (baseline vs best:
полный диапазон + OOS 20240817-20260816, fee 0.0015).

**Факт по hyperopt:** все прогоны (4 волны × 5 пар, 300 эпох, `-j 1`,
SortinoHyperOptLoss, binance 1d 20190720-20260816) убиты OOM killer (rc=137/143):
на хосте 7 ГБ RAM со swap, занятым на 100%, полноценный hyperopt нежизнеспособен.
`.fthypt` пустые (эпохи при kill не сбрасываются). Единственный кандидат 56/56
(BTC) извлечён из live-строк «* Best» лога частичных эпох — источник ненадёжный.

или на машине ≥16 ГБ RAM (либо меньше эпох/диапазона), затем повторная
OOS-валидация тем же `validate_hyperopt.py`.
